## 0. Shape and invariants (unchanged from `land.sh`)

- **Owner's command, main checkout only, never pushes** (`land.sh:3-12, 484-496, 665-666`).
  "Mostly refusals. The merge itself is one line" (`:8`).
- **One branch per invocation**; `air land A && air land B` is the queue (merge-automation §4.1
  "Never land two branches in one invocation"; §6 "Bisecting a batch of two is `make land A &&
  make land B`").
- **Rewind on any red** with `git reset --hard "$PRE"`, safe *only because nothing is pushed*
  (`land.sh:504-505, 603-609, 642-656`; merge-automation §5.3).
- **Bookkeeping last, never fails the merge; `bd` down is a warning** (`land.sh:110, 659-663`;
  merge-automation §5.7).
- **Never prints a `bd` command for a human** (`land.sh:39-43`, ad-s43; `land-prove:15`).
- **CLI:** `air land <worker> [--sha X] [--allow-main] [--allow-no-digest] [-m MSG]
  [--close-beads] [--print-digest] [--json]`. `<worker>` maps to `refs/heads/worktree-<worker>`
  (`land.sh:5,111`). The env forms `BRANCH=`, `ALLOW_MAIN=1`, `ALLOW_NO_DIGEST=1`, `MESSAGE=`,
  `MERGE_SHA=`, `PRE=` are honoured for Makefile/`land-prove` compatibility (`land.sh:15, 492,
  541, 577, 461, 467`).
- **`land-prove` compatibility:** adopter's prover hard-codes `bash "$ROOT/scripts/land.sh"
  --close-beads` / `--print-digest` with a fake `bd` first on `PATH` (`land-prove.sh:120, 281,
  404`). At M1 `scripts/land.sh` becomes `exec air land "$@"` (env passthrough) and Air must
  reproduce every string the prover greps (listed in §8). Air also carries the same prover, ported,
  as `air selftest land`.

## 2. Land by sha (`--sha X`)

**Ask (verified):** backend §4 "reported f854145 green, then merged frontend-leaning + did ad-o5fi
and the tip went red; had to re-report 'land f854145 not tip'; land.sh takes the branch ref only,
so the coordinator held the land"; backend §7(d) "`land` should accept a SHA, not only a ref, so a
green point survives later commits"; interview synthesis item 1 "land-by-sha (land takes a ref
today; a green point should survive later commits)"; plan 0001 §4.

**Semantics.**

- `X` must resolve to a commit and satisfy `git merge-base --is-ancestor X refs/heads/worktree-<w>`;
  otherwise refuse (step 5b). Landing an arbitrary commit that is not on the worker's branch is
  not landing that worker's work, and the close rules (§5) key on the worker.
- Without `--sha`, `X = $(git rev-parse refs/heads/worktree-<w>)`. With `X == tip` behaviour is
  identical to today.
- **X not the tip: land X only. The branch keeps its later commits.** Every range in the flow is
  computed against X, not the branch: digest set `HEAD...X`, `bead_index` range `HEAD..X`,
  `git diff --stat HEAD...X`, the merge is `git merge --no-ff X`, and `closing_trailers` and
  `is_contained` run over `PRE..MERGE_SHA` (unchanged) — so a `Closes:` trailer in a commit
  *after* X closes nothing, and a peer branch is "contained" only if it is an ancestor of the merge
  commit (i.e. of X). Nothing about later commits reaches main or bd.
- Default merge message is `Merge worktree-<w> at <X-short>` (git's own default for a raw
  commit is `Merge commit '<sha>'`, which loses the branch name); `-m`/`MESSAGE=` overrides.
- Afterwards the branch is `N = rev-list --count X..tip` commits ahead of main; the agent's
  `git merge main` is clean by construction (X's tree is already an ancestor). The final line
  becomes `The worktree stays — reuse it. N commit(s) after <X-short> are still only on the
  branch. The agent picks this up with: git merge main`.
- Refusal-by-rewind on X does *not* mean the tip is bad, and vice-versa; the receipt says which
  sha was tried.

**Receipt (`landings` row, plan 0001 §2 row 5 + measurement-spec §5 columns).** `worker`,
`sha = X` (what was landed), **new column `tip_sha`** (branch tip at land start; `tip_sha == sha`
when no `--sha`), `merge_commit`, `result` (`landed` / `rewound` / `refused` / `rollback_failed`),
`failing_step` (one of `regenerate:<name>`, `install`, `type-check`, `lint`, `docs-check`,
`fitness`, `verify`, `merge-conflict`, or the refuse step name), `verify_run` (id of the merged-tree
run, §4), `verify_run_at_sha` (id of the worker's recorded run at X, or null), `attempt_no`,
`started_at`/`finished_at`, `beads` (closed by this landing, with the rule that fired), `pre_sha`.
`sha ≠ tip_sha` is exactly "landed by sha"; `rev-list --count sha..tip_sha` at land time is stored
as `commits_left` so the round metrics can count how often the green point diverged from the tip.

**Spec.**

- **Step 14 (regenerate) runs after the merge and before install/fast checks**, from a per-repo
  list `regenerate = [{name, cmd}]` (adopter default: `router.d.ts` →
  `rm -f app/.expo/types/router.d.ts`; deletion, because that is the state every worktree
  verified in and no regeneration command is verified here — a repo may substitute the real
  generator). Each entry is tee'd like every other step. Nothing tracked is touched (the list is

- **`yarn install` stays unconditional** (`land.sh:589-610`; the 294 s type-check failure at

- **Every step from 13 onward is tee'd** to `.air/logs/land/<landing-id>/<NN>-<step>.log`

  the full path; the `Re-run it for the output:` hint is removed. The `verify_runs.log_path`
  column points at the same file.
- Applies to `make verify` too: verify's own `logs/verify.log` is per checkout and gets
  overwritten by the next run; the landing copy is per landing and kept with the receipt.

## 4. The recorded-green check

**Ask (verified):** coordinator §6(iv) "Self-reported 'verify green' carries the sha implicitly;
make it explicit and machine-checkable (sha + exit code in a file), because 'green' drifts within
minutes"; frontend §7(a) "let the LAND check that recorded sha equals the branch tip"; plan 0001
§4 "a check that the recorded green sha == what is being landed".

**Rule: land never blocks on a claim, and never blocks on the *absence* of a record either.** The
gate is, and stays, the merged-tree verify (`land.sh:648-657`; frontend §4: "'green at my HEAD' and
'green where it lands' diverged once"). The record is used to *inform* and to *receipt*:

1. Query `verify_runs` for `(worker, sha = X, kind = verify, exit = 0)`. Print the newest as
   `verified@X: run <id>, exit 0, <ts>, trigger <t>` — or, if none, `⚠ no recorded verify at X`
   plus the worker's newest green sha G if any: `last recorded green is G (N commit(s) before X)
   — land --sha G lands the green point instead`. Advisory only; the run continues.
2. If a red run at X is the newest record: `⚠ newest recorded verify at X is RED (run <id>)`,
   still advisory — the merged tree decides.
3. `air land` **always** records its own merged-tree run: `verify_runs` row with `worker =
   <worker>`, `sha = MERGE_SHA`, `kind = verify`, `trigger = land`, `exit`, `failing_step`,
   `log_path` — even when the result is a rewind (then `sha` is the merge commit that no longer
   exists on `main`; it is kept as an object by reflog and the row keeps the log). If X had no
   record and the merged tree is fast-forwardable (`merge-base --is-ancestor HEAD X`), the merged
   tree *is* X's tree, and the row also sets `same_tree_as = X` so the hand-over gate can treat X
   as verified. In the general case it does not: a green merged tree says nothing about X alone.
4. The receipt links both ids (`verify_run`, `verify_run_at_sha`) so `air metrics` can report
   "landings whose sha had no recorded green" — that number is the drift-incident count the
   coordinator wanted (§6(iv)) and the plan keeps as a landing-time check (0001 §8).

Why not refuse when the record is missing: (a) M0 ships the hand-over gate in advisory mode (plan
0001 §11.2), so records will be missing for a while; (b) a refusal on a missing record is a
refusal on bookkeeping, and "a guard the owner cannot get past gets deleted" (`land.sh:510-511`);
(c) the ledger is `rm -rf`-safe by design (0001 §2 footer). A future `--require-green` flag is
one line and is not in M1.

## 5. Close by evidence (ported from `close_beads`, `land.sh:38-260`)

Unchanged rules; the ledger only *observes* them (writes `landings.beads` and
`claims.release_reason = landed`). Verbatim from the script:

- **Status is the non-negotiable filter:** only `awaiting_review` closes; `in_progress` "means
  claimed and never handed over … a merge must NEVER close that, no matter which of the rules
  below points at it" (`:48-51, 134-139`).
- **Which beads = union of three rules** (`:53-62`): (1) BRANCH — `assignee == <worker>`;
  (2) TRAILER — a closing keyword `close[sd]?|fix(e[sd])?|resolve[sd]?` immediately followed by
  `fd-…` in a commit message inside `PRE..MERGE_SHA` (`:82-94`; a bare mention closes nothing);
  (3) CONTAINMENT — the assignee names a live worktree whose `worktree-<a>` branch is an
  ancestor of the merge commit (`:96-107`). Anything matching no rule is **reported, not
  closed** (`:73, 230-246`).
- **Order without a model:** attempt every selected bead, repeat while anything succeeded, ≤ 20
  passes; roots-first falls out of bd's own blocked/open-children guards (`:164-169, 181-208`).
- **Actor:** `--actor <bead's own assignee>` (never the branch's, never `--force`); a bead with no
  assignee gets no `--actor` flag (`:171-180, 192-196`).
- **Reason string:** `merged into main as $MERGE_SHA by 'make land BRANCH=$BRANCH'; make verify
  green on the merged result; matched by rule: $rules; assignee ${assignee:-<none>}` (`:191`) —
  Air keeps this text (with `air land <worker>` in place of the make invocation, and `at <X>` when
  `sha ≠ tip`; `land-prove:206-208` greps for the sha and the branch name only).
- **Reports, in words, no command** (`:210-246`): `COULD NOT CLOSE, and these are still open`
  with the last refusal per bead and `Nothing was forced. Read the reason above and fix the cause,
  not the guard.`; `⚠ claimed by <w> and NEVER handed over — NOT closed`; `⚠ named by a closing
  trailer but still in_progress — NOT closed` ("a trailer is a claim about the code,
  awaiting_review is a claim about the work"); `Awaiting review, matched by NONE of the three rules
  and so left open` with per-bead cause (`that worktree is live and its branch is NOT in this
  merge` / `assignee is not a worktree — BEADS_ACTOR was unset when it was claimed; no trailer
  names it`); open `friction` beads; `.beads/issues.jsonl is now dirty`.
- `--close-beads` requires `MERGE_SHA` ("Naming the sha is the act of asserting that the merge
  happened", `:458-462`) and tolerates a missing `PRE` (`:463-467`).
- Ledger addition (M1): after each successful `bd close`, `claims.released_at = now`,
  `release_reason = landed`; the receipt's `beads` array carries `{id, rule, assignee}`.

## 6. Batching / bisecting — when it earns its place (recommend: not in M1)

**What the primaries say.** bors-ng: "As commits are reviewed, bors lumps them into a queue of
batches. If everything passes, there will just be two batches; the one that's running, and the
one that's waiting to be run. … If the build fails, bors will follow a strategy called
'bisecting'. Namely, it splits the batch into two batches, and pushes those to the queue"; a
single-PR batch that fails "gets kicked back to the creator so they can fix it" (bors-ng README,
fetched 2026-08-18). GitHub merge queue: FIFO temporary branches, "the merge queue recreates the
temporary branch" without a failed PR; knobs `build concurrency` (1–100), min/max PRs per group,
wait time (GitHub docs, fetched 2026-08-18); requires a remote and `merge_group` CI and is not on
the Team plan (`specs-guards-tooling.md` row 30). Gas Town Refinery: "Rebase A..D as a stack on
main … Run tests on D (tip of stack) … Fast-forward merge all 4 → done … Binary bisect → test B
(midpoint)"; "Gates (test command, lint, etc.) are pluggable. The batching strategy is core."
(`docs/design/architecture.md`, fetched 2026-08-18; `beads-and-gastown.md` §2.4). Every one of
these exists to amortise a **slow gate over a deep queue** — bors's own steady state is "two
batches", the running one and the waiting one.

**adopter's numbers.** `make verify` is ~35 s warm / ~68 s after an edit (`verify-timings.md`);
the worst measured land was 294 s and was an install bug, not the gate (`land.sh:592-596`).
Lands per round: 0 for 2 h then a burst; four branches, one lander (coordinator §6(i)); queue depth
at land time was ≤ 4 and typically 1–2. Batching two branches saves at most one verify (~1 min)
and costs a bisect on red — which, at depth two, is `air land A && air land B` (merge-automation
§6). The note's warning stands unchanged: "a bug in `make land` either refuses everything or
refuses nothing, and both look like the system working" (§5.9); a batcher is more of that code.

**Trigger, measured by the ledger** (both must hold for a full round, `air metrics --round`):

1. **Serialisation cost:** `Σ over landings of (queue_depth_at_start − 1) × land_duration` ≥ 30 min
   per round, where `queue_depth_at_start` = number of `awaiting_review` claims with a landable
   branch at `landings.started_at` (a new derived field; `land_duration = finished_at −
   started_at`) — i.e. workers actually waited on the lander because of the gate, not because
   the owner was elsewhere (`L_wait` with the owner idle is *not* this).
2. **Volume:** ≥ 8 landings/day *and* median `queue_depth_at_start` ≥ 3.

Below that, the cheaper moves are: shorten verify (`ad-qjf` line, `verify-timings.md`), land in
the background and report (merge-automation §5.1), and let workers land-by-sha earlier. When it
trips: bors's own algorithm (batch, test tip, split in halves on red, single failure kicked back)
on top of §1 — never LLM-driven, never a daemon (0001 §9). Multiclaude's "CI is the only gate"
stance (`prior-art §C2`) is the one to avoid: here the owner reads the digest first
(`land.sh:538`).

## 7. Conflict handling — clean, or refuse with the exact command

Overstory's ladder is clean merge → same-file non-overlap heuristic → Sonnet-assisted merge →
human escalation, with a sentinel-file merge lock and dry-run prediction (`prior-art §B1.6`;
README "FIFO merge queue with 4-tier conflict resolution", fetched 2026-08-18). Air ports **tier 1
only** and the refusal: `git merge --no-ff X`; on any conflict `git merge --abort` and print
`merge failed — main is untouched` / `Conflicts belong to the agent that wrote the branch:` /
`    cd .claude/worktrees/<w> && git merge main` (`land.sh:582-587`; merge-automation §4.1 "Never
resolve a conflict"). With `--sha X` the printed command is the same — the agent resolves at the
tip and hands over a new sha; Air prints `then hand over the new sha; land --sha <it>` after it.
No heuristic merge (a "non-overlapping same-file" merge is exactly the class that is green alone
and red together, `land.sh:655`), no LLM tier, no lock (one lander, one process; `set -uo` and
the dirty-tree refusal are the lock — revisit with §6's trigger), no `rerere`. Optional and cheap
but **not required for M1**: `air land --dry-run` = `git merge-tree --write-tree HEAD X` (git ≥
2.38) to answer "would it conflict" without touching main — Overstory's dry-run, one line, useful
for the coordinator's "merge now" nudges; note it in the plan as M1-optional.

## 8. Probes (red/green), `air selftest land`
